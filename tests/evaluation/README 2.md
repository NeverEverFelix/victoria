# Multi-Agent Evaluation Harness

`multi-agent-readiness.test.ts` runs the existing `VictoriaAgent` and a scripted specialist team through the frozen starter corpus in `fixtures/multi-agent-scenarios.ts`. It asserts both flows against expected MVP outcomes and verifies that the comparison creates no ledger entries.

`multi-agent-conversations.test.ts` exercises multi-turn cases for low-confidence intent, specialist/core estimate disagreement, and a temporary Savings Reasoning failure. It verifies clarification context, recovery, pending-proposal boundaries, clarified goal-target precedence, and exact approval before mocked ledger writes. These scenarios use mock specialists and remain contract checks, not model-quality evidence.

The scripted specialists use `MockLlmAdapter` and deterministic fixture logic. This is a plumbing and contract-parity check only. Its local elapsed times are not representative provider latency and its output has no model token or price data.

In the frozen provider corpus, `expectedIntent` is the financial-moment classification for the current utterance; `expectedAction` also reflects conversation context. For example, a short confirmation may classify as `unclear` on its own while still authorizing the exact pending proposal through the separate approval policy.

`metrics.ts` computes nearest-rank p50 and p95 summaries across turns. The standalone `ProviderUsageReporter` collects one record per successful provider response with role, elapsed time, input/output tokens when returned, and request ID when returned; it can provide an immutable snapshot, JSON Lines output, per-role timings, and a per-role usage summary using a caller-supplied dated rate card. Cost is left unknown when any response is missing token usage. The agent does not produce reports. This collector is in-memory and does not track retries. A provider-backed evaluation should use the same corpus and summary shape, record model and prompt versions, and retain per-role timings. Do not compare the scripted mock timings with the proposed service targets.

The frozen 50-turn synthetic corpus is `fixtures/provider-eval-v1.json`; evaluation design and blinded review instructions are in `../../docs/architecture/multi-agent-evaluation-protocol.md`. `templates/blinded-review.csv` is the reviewer sheet and `templates/provider-run-report.json` defines run metadata and summary fields. Expected safety outcomes must stay fixed during a comparison. Use a separate holdout set when tuning prompts or routing. Both the offline mock-contract runner and the opt-in provider comparison consume all 50 cases.

The provider comparison records `financialAssessmentRoute` per target turn and aggregates the fixed categories per arm (`assessed`, `skipped_plain_question`, `skipped_model_dialogue`, `resolved_pending_amount`). These counters are content-free routing evidence. Failed turns with no assessment outcome retain `null` and are not counted as skips. The report template includes per-turn target provider call count, provider elapsed time, unaccounted turn time, all four role latencies and usage fields, cost summaries, and route categories; a test checks the emitted report against that template. Compare route counts alongside provider usage and latency; counts alone do not establish cost savings or response quality.

The companion setup map in `fixtures/provider-eval-v1-setups.ts` seeds the pending $20 proposal required by P31–P35, stale-estimate context for P49, and P50's prior $20 ledger entry through normal proposal and exact-approval turns. `applyProviderEvalStateSetup` applies those preludes to an agent and checks actions, pending approval, and ledger state. The setup map is separate from the frozen JSON; a test verifies the corpus SHA-256 remains unchanged.

`conversation-intent-disagreement.test.ts` runs a frozen, synthetic six-case set through the deterministic intent plan, advisory-plan validation/shadow comparison, and turn coordinator. It checks that disagreement is observed, that deterministic action requests remain the coordinator's action description, and that advice, historical, negated-transfer, and pending-workflow cases keep their expected route. The fixture's advisory plans are scripted inputs, not model outputs or quality evidence. The cases are regressions from the architecture review and prior development work, so they are not a held-out set; use a separate, independently labeled corpus for tuning decisions and blinded evaluation.

`npm run eval:provider:mock-comparison` replays all 50 frozen target turns through two local arms: the deterministic core baseline and the scripted specialist team. It probes each target's intent separately using the corpus transcript context, then runs the target turn against any state established by the setup prelude. It emits pass counts and IDs for intent, action, and amount mismatches, plus safety-failure counts. The returned report builder retains runtime classifications, user-facing responses, setup actions, ledger deltas, and safety findings. The command makes no network requests. These scripted arms validate evaluation plumbing and expose deterministic contract mismatches; they are not the provider comparison or quality evidence.

`npm run eval:provider:comparison` runs the live provider-backed comparison. It uses one OpenAI Financial Moment baseline arm and one full provider specialist arm, with mock memory and ledger tools. The intent probe is a separate provider request for each target, including confirmation turns that the runtime handles directly. Setup prelude calls count toward provider usage and cost. Target-turn latency is now reported alongside the number and summed elapsed time of provider responses recorded during that target; the remaining elapsed time is labeled as time outside recorded successful provider calls, not attributed to a specific cause. The command requires `CONFIRM_LIVE_COMPARISON=1`, a local real API key, `APP_ENV=local`, `MONEY_MOVEMENT_MODE=mock_ledger`, a real `OPENAI_EVAL_MODEL`, and a dated caller-supplied rate card through `OPENAI_EVAL_RATE_CARD_DATE`, `OPENAI_EVAL_INPUT_USD_PER_MILLION`, and `OPENAI_EVAL_OUTPUT_USD_PER_MILLION`. It makes sequential provider calls across both arms and may incur charges. The report includes synthetic scenario responses, per-role latency and cost summaries, per-turn cost, and raw request IDs; it contains no real user messages or credentials. A mocked Responses API test exercises report plumbing without credentials; ordinary `npm run check` skips the live comparison.

## Provider smoke evaluation

`RUN_PROVIDER_CONVERSATION_CHALLENGE=1 CONFIRM_LIVE_CONVERSATION_CHALLENGE=1 npx vitest run tests/evaluation/provider-conversation-challenge-live.test.ts` challenges a real local provider across a pending $19.95 proposal, a detailed ordinary topic shift, ambiguous approval, a read-only event-history question, and a final exact approval. It also runs an unpunctuated plain-dialogue turn without a pending workflow to exercise the model-approved assessment skip. It uses mock memory and ledger adapters only and asserts that no entry exists until the exact approval. The test records provider roles/timing, assessment route categories, and content-free conversational reply fallback outcomes/rate; it never emits credentials. It requires `APP_ENV=local`, a real `OPENAI_API_KEY`, a provider model, and `MONEY_MOVEMENT_MODE=mock_ledger`; it may incur API charges and is skipped by normal checks.

`npm run eval:provider:financial-moment` runs an opt-in OpenAI-backed check over the original seven starter cases. It defaults to `gpt-6-luna`; override with `OPENAI_EVAL_MODEL` if needed and set `OPENAI_API_KEY` in the process environment. It makes seven provider requests and can incur API charges. The report includes model/schema/prompt versions, classification and amount contract results, latency samples, token counts, and request IDs. It does not consume `provider-eval-v1.json`, compare complete runtime arms, estimate cost, or include blinded human review. It is a smoke check only and does not satisfy the 50-turn readiness gate. Ordinary `npm run check` skips this live evaluation.

`npm run agent:smoke:provider-team` loads local config through Next's env loader and runs one synthetic avoided-spend turn through the complete provider team, using mock memory and ledger tools. It stops before user approval and asserts that the mock ledger remains empty. It may make up to three provider requests and incur charges. The command fails unless `APP_ENV=local`, `OPENAI_AGENT_TEAM_ENABLED=true`, `OPENAI_MODEL` is a real model ID, and `MONEY_MOVEMENT_MODE=mock_ledger`. It is opt-in and skipped by normal test/check commands.

For copyable setup and run commands, see [`docs/provider-agent-team-smoke.md`](../../docs/provider-agent-team-smoke.md).
